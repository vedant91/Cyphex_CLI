Cyphex — real-time cyber safeguards

How Cyphex contains the risk of automated security testing, exactly which stage needs verification, and what to put in the application. For the person preparing the submission — not a claim of approval.

1What Cyphex is

Cyphex is an AI security scanner that tests a team's own application for vulnerabilities and writes the fixes. It ships two ways: a local command-line tool that runs on the owner's own GPUs, and a thin MCP server that hands the testing work to a host coding agent (Claude Code). It is authorized testing: the operator runs it against code they own, on a target they control, with their consent recorded at the start of every run.

Most of the pipeline is reading and reasoning — mapping routes, reading code for bug classes, voting on findings, writing patches. None of that is offensive content. One stage is: proving a finding by sending a real request to the running app.

2What needs verification

Only one capability: a Claude model that adapts attacks in real time — reads the app's response and crafts the next request — against a target inside the operator's sandbox. This is the "deep DAST" stage when it is driven by a frontier model rather than a fixed scanner.

Anthropic's real-time cyber safeguards stop this today, on both Sonnet and Opus, before any request is sent. That is the correct behaviour for an unverified caller. The Cyber Verification Program is the route to run it legitimately: support.claude.com/en/articles/14604842-cyber-verification-program.

Everything else in Cyphex runs unaffected without verification. This packet is only about enabling the adaptive live-attack stage.

3Why the sandbox cannot exempt it

A natural objection: "every request stays inside an isolated Docker network, nothing leaves the machine, so the safeguard should not fire." It does not work that way, and that is the right design:

  • The safeguard judges the content of the work — a model authoring a working exploit — not the network it is aimed at. The same payload is dangerous whether it is pointed at a sandbox or at a production host.
  • The classifier cannot see or verify a sandbox claim. "It's only local" is exactly what a misuse attempt would also say.
  • So the honest path is not to argue the content is safe, nor to reword it until it passes. It is to have Anthropic verify the operator and the use case, and relax the safeguard for that verified party. That is what the program is for.

Cyphex does not try other models or phrasings to get the adaptive stage through. That would be probing a safeguard. Until the operator is verified, Cyphex runs a deterministic stage instead (§5).

5Behaviour before verification (shipping today)

The live-attack stage is deterministic. dast_recipe(job_id) returns a command that runs Nuclei — a standard third-party scanner with its own template library — from inside the sandbox. The operator runs that tool; submit_dast lets the MCP parse the output and mark proof itself. No model writes attack requests, so the stage is a plain tool run and is never gated.

The trade-off is honest and stated in the report: a template scanner does not adapt. Findings it cannot reach stay "confirmed by code reading" rather than "proven by a live attack". The product is useful at this tier; verification is what unlocks the adaptive tier.

6Behaviour once verified

After the operator's organisation is verified, the adaptive live-attack agent can be enabled. It reads each response and crafts the next request, still bounded by every control in §4: the sandbox target only, the recorded consent, the guardrails, the audit log. Verification changes who is allowed to run the stage, not what the stage is allowed to touch.

This packet does not ship an enabled adaptive attacker. That agent is switched on only after verification, and even then Anthropic's safeguard remains the authority — a flag on the operator's side cannot and does not disable it.

7Application checklist

Gather these before applying through the program page linked in §2.

  • Organisation identity and a point of contact for the security work.
  • A one-paragraph description of Cyphex and the authorized-testing use case (§1).
  • The specific capability requested: a Claude model adapting attacks in real time against the operator's own sandboxed applications (§2).
  • The containment and consent controls already in place (the table in §4), with the sandbox isolation model called out.
  • Confirmation that targets are always owned or controlled by the operator, with consent recorded per run.
  • The audit trail you keep (SECURITY_LOG.md and job records), available for review.
  • A statement that, unverified, Cyphex runs only the deterministic stage and does not attempt to bypass the safeguard (§3, §5).
